# ADR-0008: Edge Platform Deployment Strategy

**Status**: Accepted  
**Date**: 28-07-2026  

## 1. Status
Accepted

## 2. Context
The repository currently contains an existing deployment configuration file (`vercel.json`) alongside complex legacy build commands in `package.json` (`build:legacy`) that manually invoke concurrent build processes across separated `client/` and `api/` workspace directories before manually copying output files into a root `dist/` folder. This legacy orchestration is fragile, prone to file copying synchronization errors, and structurally incompatible with Next.js App Router optimized static compilation and serverless execution capabilities. To ensure deterministic build verification, seamless SSL certificate automation, high-speed global CDN delivery, and zero-downtime production releases, deployment orchestration must transition to standard modern cloud edge engineering practices.

## 3. Decision
We adopt Vercel as the canonical hosting and continuous deployment cloud edge platform for the portfolio application. We mandate standard Next.js App Router native build execution (`next build`) as the singular operational deployment pipeline, entirely decommissioning custom shell copy scripts and legacy multi-folder build commands from `package.json`. Production domain cutovers must be preceded by mandatory staging verification across automated ephemeral branch preview URLs generated by Vercel CI pipelines.

## 4. Consequences
* **Positive Engineering Consequences**:
  * Instantaneous global static asset delivery and single-digit millisecond routing response times via Vercel edge CDN networks.
  * Zero maintenance overhead for SSL/TLS encryption certificate rotation, DDoS protection mitigations, or web HTTP security protocol optimizations.
  * Uncompromising build integrity: production branch cutovers execute automatically upon clean completion of static typechecking, linting, and Next.js static asset generation during build runs.
  * Complete decontamination of `package.json` scripts, reducing operational compilation complexity to standard industry defaults (`npm run build`).
* **Negative Trade-offs and Limitations**:
  * Creates architectural reliance on Vercel platform infrastructure conventions for Next.js image optimization and edge middleware routing execution.
  * Migrating production domain traffic away from Vercel edge servers to standard self-hosted Linux VPS Docker containers in the future would require adding explicit standalone server output configurations within `next.config.ts`.
* **Compliance Obligations**:
  * Any adjustment to HTTP response redirection, routing headers, or caching controls must be committed explicitly to versioned configuration files (`next.config.ts` or `vercel.json`) rather than configured manually through unversioned web dashboard administrative settings.

## 5. Alternatives Considered
* **Self-Hosting Dockerized Next.js Node Server on AWS / DigitalOcean VPS**: Package application into a Docker container image running a persistent Node.js server instance on a cloud virtual private server. *Reason for Rejection*: Over-engineered operational complexity for a read-heavy engineering portfolio; incurs continuous hourly computing runtime costs, demands manual operating system security patching, and lacks instantaneous global CDN edge distribution without complex load balancing configurations.
* **Deploying Static Export (`output: 'export'`) to GitHub Pages**: Force completely flat HTML file exports and host on simple GitHub repositories. *Reason for Rejection*: Prohibits utilizing dynamic Server Route Handlers (`src/app/api/*`) needed for planned backend application security tools, OSINT diagnostic utilities, and real-time HTTP security request inspections in future project evolution phases.
